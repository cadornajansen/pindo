# LocalTutor product scope

Status: proposed tutoring scope, dated 2026-10-09; app code remains at the bootstrap milestone.

## Problem and intended outcome

Filipino educators preparing lessons need help finding an unfamiliar software control; LocalTutor aims to give one locally generated instruction and highlight the next accessible control so the teacher can perform the action and learn it.

The primary user is an educator preparing a lesson slide. This is a working audience assumption from the team brief, not a completed user-research finding. The app's working name is LocalTutor and the repository is `pindo`; no branding change is included here.

User story: **As a teacher preparing a PowerPoint lesson, I want to ask in English, Filipino, or Taglish where to click next, so I can add a picture without leaving my task to search for instructions.**

## One required demonstration

**Insert an existing local picture into a PowerPoint lesson slide.** Start with PowerPoint open on a recorded slide, a known ribbon state, and a prepared sample picture. The teacher summons LocalTutor, requests help, receives one instruction/highlight, performs the action, and requests another step when needed.

The demo ends when the teacher confirms that the prepared picture is on the slide. The assistant does not click, select a file, manipulate the picture, or save the presentation. A supported dialog is part of the task only after its accessible controls are captured and validated.

This is the single highest-priority path. Other slide tasks are optional future validation scenarios; adding a second task is not required to complete this slice. AppBuildersPH remains the team's stated event target; official submission requirements belong in [the compliance checklist](HACKATHON_COMPLIANCE.md).

## Priorities

| Priority | Included capability | Boundary |
|---|---|---|
| Must | Summon the floating palette and retain the original PowerPoint window | Use the existing hotkey/window behavior; preserve collision recovery |
| Must | Accept a teacher's written request | Empty input is rejected; mock and actual tutoring states remain distinguishable |
| Must | Capture a small relevant UI Automation snapshot | Source-window controls only, with snapshot-local IDs and actual bounds; no screenshot collection |
| Must | Run local next-step inference | One brief instruction and one captured target at most; no generated commands |
| Must | Validate and highlight the next control | Reject unknown, disabled, stale, or unusable targets before showing a highlight |
| Must | Keep the teacher in control | Teacher performs every action; each new step uses fresh UI evidence |
| Must | Handle unavailable inference and unsupported UI safely | Explain the failure and a recovery action; do not guess or silently switch to cloud |
| Must | Measure the demo path before making claims | Record correct targets, failures, latency, language quality, and offline evidence |
| Must | Keep interaction clear while waiting | Visible pending state, responsive controls, cancellation, and no late result after cancellation |
| Must | Support understandable English, Filipino, and Taglish guidance | Same task and expected control across language variants; educator review required |
| Should | Refine brevity after the core behavior passes | Short, readable instructions that preserve the validated next action |
| Later | Expand PowerPoint scenarios and application coverage | Reuse the same accessibility approach only after recording task/version evidence |
| Later / optional | One independent approved local utility | Separate typed tool work; no dependency for the picture-insertion demo |

“Must” is the smallest successful tutoring product, not the current feature inventory. [PRD requirement IDs](PRD.md) and [validation cases](VALIDATION_PLAN.md) define how to accept each capability. Useful waiting/cancellation behavior is specified in FR08 even though the exact timeout still needs benchmarking.

## Optional utilities stay separate

Member 2 may prepare **one explicitly agreed local utility** through the existing typed contracts, after agreeing its input, output, validation, cancellation, and effect with the lead. A PDF, conversion, or media capability remains a candidate until the team chooses a concrete operation.

No specific tool, library, external service, or extra technology is selected by this document. Utilities must not accept arbitrary shell commands or become a prerequisite for tutoring. Their results, failure handling, and any confirmation must be tested independently before integration.

## Out of scope for this slice

- Autonomous mouse/keyboard actions, automatic file selection, or commands generated by the model.
- Model training/fine-tuning, complex retrieval pipelines, screenshot/vision fallback, or broad app support claims.
- Voice, cloud inference fallback, online service integration, or a plugin discovery system.
- Accounts, authentication, a web backend, a database, or stored conversation/lesson history.
- Full Photoshop/Canva support or a promise that third-party online apps work offline.
- Redesigning the current app, renaming its projects, or implementing another feature while documentation is being prepared.

## Success and required evidence

| Outcome | Evidence before claiming success |
|---|---|
| Teacher completes the picture task | Recorded starting state, teacher instruction, expected controls, observed steps, and teacher-confirmed picture insertion |
| Guidance is grounded | At least 90% correct target selection on labeled targetable cases; failures stay in the denominator; no-target cases reported separately |
| Response is fast enough | End-to-end p50 ≤ 5 seconds and p95 ≤ 10 seconds on the actual demo laptop, with hardware/model/sample count and cold starts disclosed |
| Language is useful | English, Filipino, and Taglish variants for the same task, with educator clarity review |
| Local/offline behavior is credible | Runtime/model prepared beforehand; network-disabled demo and outbound-traffic/capture-scope checks, reported with limitations |
| Failure is safe | Unknown targets, inaccessible controls, stale UI, missing runtime/model, timeout, and cancellation produce no guessed highlight or automatic action |

All tutoring outcomes above are **unverified targets**. Current evidence covers only mock desktop behavior and shared contracts. See [implementation status](IMPLEMENTATION.md) and [the validation plan](VALIDATION_PLAN.md) for the distinction.

## Assumptions and deferred decisions

- The demo machine has a usable Windows PowerPoint installation and accessible controls for the selected task; exact versions are not recorded yet.
- The teacher supplies a local sample picture and can perform actions manually. No online image search or download is needed for the task.
- Ollama and an explicitly downloaded model are prerequisites for future local inference; their availability does not prove tutoring works.
- `qwen3:1.7b` is an initial candidate. Final model choice, context limits, snapshot filtering, and the proposed timeout depend on measured results.
- Educator wording, pain points, and perceived usefulness need direct feedback; no interviews or classroom outcomes are claimed.
- Broader application coverage, persistent history, and a concrete optional utility are deferred product decisions.

Read [the PRD](PRD.md) for behavior and acceptance, [the data model](DATA_MODEL.md) for current versus proposed data flow, and [the README](../README.md) for what teammates can run today. This documentation defines the target without starting another implementation feature.
